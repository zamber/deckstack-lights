deckstack-lights

A reference deckstack plugin that drives the lights on a lights.lan HueMux bridge. It is a normal process, a manifest, one action, and host-mediated HTTP only.

View source on GitHub Read the README deckstack site HueMux

What a plugin gets

A deckstack plugin is not a library and not a daemon extension. It is an ordinary OS process that the host starts, and everything it can do is spelled out in its manifest:

  • A normal process. The host spawns it from the manifest's command. It has no HID access and no ambient authority. It cannot even open a socket.
  • Newline-delimited JSON on stdio. The host speaks the plugin wire protocol to it. Every side effect the plugin wants is a request the host may refuse. That includes reading state, writing state and making HTTP requests.
  • One network grant. net:lights.lan. The daemon checks the URL host against that grant and /policy/net/allow_hosts before it makes the request itself.
  • Validated parameters. The action.s params are a JSON Schema, and the daemon validates them before the plugin runs.
  • Config as data. Read from /plugins/lights/config when present, or from the durable /plugins/lights/state/config. A room allowlist is deployment policy, not code.

How a key press reaches a light

The host mediates every hop. The plugin process only ever asks. The daemon decides and acts:

A key press becomes a binding step, then the plugin host, the plugin process, an sdk.http request, the policy check, HueMux and the light. The policy check runs inside the daemon: it matches the URL host against the net:lights.lan grant and /policy/net/allow_hosts, then performs the HTTP request itself. The plugin never opens a socket.

The manifest

Everything the host needs to know about the plugin is declared in manifest.json. It holds identity, launch command, capabilities, actions:

{
  "id": "lights",
  "name": "lights.lan bridge (HueMux)",
  "version": "0.1.0",
  "description": "lights.set {room, light, on, brightness, color} on the lights.lan HueMux bridge over host-mediated HTTP. The only network capability is net:lights.lan.",
  "command": ["/usr/bin/python3", "plugin.py"],
  "actions": [
    {
      "id": "set",
      "name": "lights.set",
  "description": "Set a light in a room on the lights.lan HueMux bridge {room, light, on?, brightness? 0-100, color? '#rrggbb'}. Host-mediated HTTP only, with the single net:lights.lan grant.",
      "params": { "…": "JSON Schema, see below" }
    }
  ],
  "capabilities": ["state.read", "state.write", "net:lights.lan"],
  "resources": {"cpu_s": 10, "nproc": 64, "nofile": 64, "as_mb": 1024}
}

The daemon schema-validates this file when it spawns the plugin, and requires the plugin's register message to equal it.

The action: lights.set

One action, with JSON-Schema params the daemon validates

One action, with JSON-Schema params. The daemon validates them before the plugin runs and refuses a bad value with E_SCHEMA:

paramtyperequirednotes
roomstringyes1 to 64 chars, [A-Za-z0-9_-]
lightstringyessame charset
onbooleannoon / off
brightnessintegerno0 to 100
colorstringno#rrggbb
"params": {
  "type": "object",
  "properties": {
    "room":       {"type": "string", "minLength": 1, "maxLength": 64,
                   "pattern": "^[A-Za-z0-9_-]{1,64}$"},
    "light":      {"type": "string", "minLength": 1, "maxLength": 64,
                   "pattern": "^[A-Za-z0-9_-]{1,64}$"},
    "on":         {"type": "boolean"},
    "brightness": {"type": "integer", "minimum": 0, "maximum": 100},
    "color":      {"type": "string", "pattern": "^#[0-9a-fA-F]{6}$"}
  },
  "required": ["room", "light"],
  "additionalProperties": false
}

Capabilities

capabilitywhat it grants
state.readread plugin state, e.g. /plugins/lights/config
state.writerecord results under /plugins/lights/state
net:lights.lanthe only network grant: host-mediated HTTP, and only to lights.lan

net:lights.lan is the plugin's sole network capability, and it is still not enough on its own: the daemon also checks the URL host against /policy/net/allow_hosts before performing the request. The glob is anchored and * matches exactly one DNS label, so the grant allows lights.lan only. It refuses lights.lan.evil.com, lan, a.b.lan, x.lights.lan with E_CAP. Each refusal is counted in stats.violations. The request goes out as sdk.http("GET", url). Request kind "net". answered by the daemon, which resolves DNS and connects itself. The plugin process never opens a socket.

Config as data

The plugin reads its config on every invoke. It reads /plugins/lights/config when present, or from the durable plugin-owned /plugins/lights/state/config. Room and light ids are never hardcoded. The allowlist is deployment policy:

ds set /policy/net/allow_hosts --json '["lights.lan"]'
ds set /plugins/lights/state/config --json \
  '{"bridge_host":"lights.lan","bridge_port":80,"allow_rooms":["salon"]}'
{"bridge_host": "lights.lan", "bridge_port": 80, "allow_rooms": ["salon"]}

A room outside allow_rooms is refused with E_CAP before any bridge request is made.

Install and invoke

The plugin needs the ds-plugin-py SDK. Install it with pip once published, or from a checkout of the deckstack repository next to this one (../deckstack/plugins-py or $DS_PLUGIN_PY_ROOT overrides):

pip install ds-plugin-py        # once published
# or: keep a clone of https://github.com/zamber/deckstack next to this repo

DEST=${XDG_DATA_HOME:-$HOME/.local/share}/deckstack/plugins/lights
mkdir -p "$DEST"
cp plugin.py "$DEST/plugin.py"
python3 make_manifest.py "$DEST/manifest.json"

ds daemon start --device virtual:/tmp/vdev.sock --data-dir /tmp/dsdata

Then bind a key (or any topic) to the action and emit it:

ds bind deck/control/keys.0/down --do \
  'plugin lights.set {"room":"salon","light":"ceiling","on":true,"brightness":80,"color":"#ff8800"}'
# trigger the binding with a key press, or over the control socket:
#   {"op":"emit","topic":"deck/control/keys.0/down"}

ds get /plugins/lights/state/last --json   # last bridge response, recorded by the plugin
ds get /plugins/lights --json              # {manifest, status, state, stats}

Tests

Testing is real, not mocked at the plugin boundary:

python3 tests/run.py     # exit 0 = green

The suite boots the real ds-vdev and ds-daemon, installs the plugin, and points it at a fake HueMux bridge (tests/fake_humux.py), a stdlib HTTP server that records every request, so the tests can assert exactly what the plugin asked the bridge to do, including that a refused room never produced a request. The run is hermetic: the suite re-execs itself in a user+mount namespace with a private /etc/hosts mapping lights.lan to 127.0.0.1. It covers manifest schema validation, boot to running, lights.set success and partial args, the allow_rooms refusal, the net glob edge matrix, the /policy/net/allow_hosts layer, params-schema refusals, and cleanup. It needs the prebuilt deckstack binaries (../deckstack/target/debug or $DS_BIN_DIR).
